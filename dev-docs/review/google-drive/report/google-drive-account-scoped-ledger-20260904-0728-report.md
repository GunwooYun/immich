## 1. `f82f49e9c` — 직전 리뷰의 C1에 대한 답

직전 리뷰가 **내 B1 수정이 UI 경로에서 절대 발동하지 않는다**고 지적했고, 확인 결과 사실이었다:
계정 전환은 반드시 Disconnect를 거치고, `disconnect()`가 `driveAccountId`를 담은 행을 통째로
지운다. 원장은 disconnect를 의도적으로 살아남는데 그것을 지키는 신원값은 못 살아남으므로 항상
fail-open이었다.

deep-reasoning 검토를 거쳐 **문제의 형태를 바꾸는 쪽**을 택했다(리셋을 고치는 대신 없앤다):

```
PK: (userId, assetId)  →  (userId, assetId, driveAccountId)
"이미 업로드됨"        →  "지금 연결된 계정으로 이미 업로드됨"
```

- 다른 계정 → 기존 행이 매칭되지 않아 백로그가 스스로 재계산된다. 감지도 리셋도 없다.
- **원래 계정 복귀 → 재업로드 0.** 리셋 설계는 이 경우 전체를 다시 올렸다.
- **원장을 지우는 경로가 사라졌다**(`deleteUploads` 삭제). `files.create`에 멱등 마커가 없어
  잘못된 리셋 한 번이 되돌릴 수 없는 중복 수천 개를 만들기 때문이다.

**배포 안전**: 기존 행은 `''`, 아직 식별되지 않은 연결도 `''` → 서로 매칭되어 배포만으로는
아무것도 재업로드되지 않는다. 입양은 **기존 토큰이 살아 있는 동안에만** 일어난다 — storage 호출
(`about.get`에 `user(permissionId)`를 **기존 호출에 얹어** 두 번째 왕복 없이)과 첫 업로드.
**연결 경로에서는 절대 입양하지 않는다** — 거기서는 토큰이 새것이라 다른 계정일 수 있고,
입양하면 원래 버그를 한 번 더 재현한다.

`files.create`에 `appProperties.immichAssetId`를 추가했다. 지금 읽는 곳은 없고, 원장이 유실·오염됐을
때 "이미 올라간 파일을 찾아 흡수"할 수 있게 하는 유일한 수단이다.

**비공허 확인**: 계정 비교를 무력화하면 **의존하는 3개만** 실패하고 나머지 2개는 통과한다
(그 둘은 비교가 결정 요인이 아닌 케이스).

## 공격해 주셨으면 하는 것

1. **입양의 안전성.** `adoptIfNewlyIdentified`가 링크 경로에서 호출되지 않는다는 것이 이 설계의
   안전 속성 전부다. 내가 놓친 다른 진입점에서 미식별 상태로 이 함수에 닿는 경로가 있는지.
2. **`''` 버킷의 수명.** 두 개의 서로 다른 미식별 계정이 같은 버킷을 공유한다(설계상 의도).
   이게 실제로 발생 가능한 시나리오인지, 발생하면 어떻게 드러나는지.
3. **PK 변경의 부작용.** 3컬럼 PK로 바뀌면서 기존 인덱스·외래키·`onConflict` 경로가 여전히
   맞는지. 특히 `recordUpload`의 3컬럼 `onConflict`가 같은 계정 재업로드에서 의도대로 도는지.
4. **`integrity.repository.sql`이 왜 바뀌었는지 나는 설명하지 못한다.** `mise //:sql`을 두 번
   돌려도 동일하게 나오므로 생성기는 결정적이다. `@GenerateSql` 메서드 하나(`deleteUploads`)를
   제거한 것이 파일 귀속을 밀어낸 것인지 봐 주기 바란다.
5. **배포 절차.** `Fork Rules` §7에 "배포 → 설정 화면 한 번 열기 → 미상 행 0 확인 → 그 뒤에야
   연결 해제" 순서를 적었다. 이 절차가 실제로 위험 구간을 닫는지, 아니면 내가 놓친 창이 있는지.
