# 구글드라이브 업로드 실패 처리 계획

라이브 배포(v3.1.0 + Google Drive, 2026-08-14) 이후의 다음 과제. "업로드가 실패하면 어떻게
되는가 / 사용자는 그걸 어떻게 아는가"에 대한 현재 상태 정리와 단계별 제안.

먼저 분명히 할 것: **질문 세 개 중 하나(중복 업로드)는 이미 완결**되어 있고, 하나(실패 시
재시도)는 절반 — 복구 경로는 있지만 사용자 눈에 안 보임 — 이고, 하나(표시·알림)는 아직
아무것도 없다. 그래서 이 문서의 실제 작업 대상은 뒤의 두 개다.

---

## 1. 현재 동작 — 이미 되어 있는 것

### 중복 방지 (질문 2-3에 대한 답)

"업로드한 걸 또 업로드하려고 하면"은 **세 겹으로 막혀 있고, 추가 작업이 필요 없다.**

| 겹 | 위치 | 막는 것 |
|---|---|---|
| ① 큐잉 전 ledger 필터 | `utils/google-drive.ts` | 이미 올라간 사진은 큐에 들어가지도 않음 |
| ② BullMQ `jobId` dedup | `job.repository.ts` | 동시에 두 경로로 큐잉돼도 작업은 하나로 합쳐짐 |
| ③ 워커의 `hasUpload` 재확인 | `uploadAsset` | 큐잉~실행 사이에 다른 경로가 먼저 올린 경우 skip |

같은 사진을 앨범 A와 B에 넣어도, 동기화 버튼을 연타해도, 백필을 여러 번 돌려도 Drive에
중복 파일은 생기지 않는다. 실제 라이브 테스트로도 확인됨(같은 사진 2장을 두 앨범에 추가 →
업로드 1회).

### 실패의 종류별 현재 처리

| 실패 | 지금 동작 | 성격 |
|---|---|---|
| 일시 오류 (429, 5xx, 403 rate limit) | HTTP 레벨에서 5회 백오프 재시도 → 그래도 실패하면 작업 실패 | 자동 복구 시도 |
| 크기 불일치 (잘린 업로드) | 부분 파일 삭제 + 작업 실패. ledger에 기록 안 함 | 실패지만 데이터는 안전 |
| 토큰 폐기 (`invalid_grant`) | 자격증명 삭제 → "미연결" 상태로 전환, 이후 전부 조용히 skip | 터미널, 재연결 필요 |
| 원본 파일 없음/못 읽음 | 경고 로그 + skip | 터미널 |
| 삭제/휴지통 자산 | skip | 정상 케이스 |
| Drive 용량 초과 | 403이라 5회 재시도 후 작업 실패 | **터미널인데 일시 오류처럼 취급** ← 문제 |

### 실패한 작업의 재시도 경로 (질문 2-1의 현재 절반)

첫 리뷰의 R1 수정으로, 실패한 작업은 큐에서 제거되어 `jobId`를 비워 준다. 따라서:

- 앨범의 **"Sync to Google Drive"** 버튼 → 그 앨범의 실패분 재큐잉
- 관리자 **큐 전체 실행(백필)** → 모든 사용자의 실패분 재큐잉
- 같은 사진을 **다른 앨범에 추가**해도 재큐잉

즉 "실패는 반드시 다시 시도할 수 **있다**"는 보장까지는 되어 있다. 단, 표현을 정확히
하면 이것은 자동 복구가 아니라 **"다음 수동 트리거 때 복구 가능"** 이다 — 예약된 백필은
없으므로, 실패한 사진은 사람이 동기화 버튼을 누르거나 백필을 돌리기 전까지 그냥 기다린다.
이걸 실제 자동에 가깝게 만드는 것이 Phase 3의 "전체 재시도" 버튼이다.

안 되어 있는 것은 그 다음: **실패했다는 사실 자체를 사용자가 알 방법이 서버 로그뿐**이다.
R1 수정의 대가로 관리자 Jobs 패널의 실패 카운트마저 사라졌으므로, 지금 실패는 완전히
침묵한다.

## 2. 격차 — 만들어야 하는 것

1. **실패 기록이 없다.** 작업이 큐에서 사라지면 어떤 사진이 왜 실패했는지 조회할 곳이 없다.
2. **터미널 실패의 구분이 없다.** Drive 용량 초과가 대표적: 백필을 돌릴 때마다 수천 장이
   전부 5회씩 재시도하고 전부 실패하는 낭비가 반복된다. 사용자가 용량을 비우기 전엔 무엇을
   해도 성공할 수 없는데, 시스템은 그걸 모른다.
3. **UI 표시가 없다.** 앨범에서 어떤 사진이 올라갔고(2-2의 "이미 업로드" 표시), 어떤 사진이
   실패했는지 화면에 없다. 설정 페이지도 연결 여부만 보여 준다.
4. **알림이 없다.** immich에는 인앱 알림 인프라(`NotificationType.JobFailed` 등)가 이미
   있는데 이 기능은 쓰지 않는다.

## 3. 제안 — 3단계

### Phase 1: 실패를 기록한다 (기반, 최우선)

새 테이블 `google_drive_upload_error`:

```
userId      uuid  (FK user, cascade)
assetId     uuid  (FK asset, cascade)
error       varchar   -- 분류된 코드: quota_exceeded | rate_limited | size_mismatch | unknown ...
detail      varchar   -- 원본 에러 메시지 (잘라서)
attempts    int       -- 누적 실패 횟수
lastFailedAt timestamptz
PK (userId, assetId)
```

- **기록 지점은 catch 하나가 아니다 — 이게 이 Phase의 핵심 함정이다** (2차 리뷰 지적).
  `uploadAsset`의 터미널 케이스들(원본 파일 없음, `invalid_grant`)은 throw가 아니라
  `return 'skipped'`로 끝나므로 catch를 지나가지 않는다. catch에서만 upsert하는 구현은
  이 경로들을 전부 조용히 놓친다. 기록 지점을 명시하면:

  | 경로 | 기록? | 이유 |
  |---|---|---|
  | catch (429/5xx 소진, 크기 불일치, unknown) | ✅ upsert | 재시도 가치가 있는 실패 |
  | skip: 원본 파일 없음/못 읽음 | ✅ upsert (터미널 표시) | 사용자가 알아야 할 상태 |
  | skip: `invalid_grant` → 자격증명 삭제 | ✅ upsert (터미널 표시) | Phase 3 알림의 트리거 |
  | skip: 자산 삭제/휴지통 | ❌ | 정상 동작, 오류 아님 |
  | skip: 미연결/기능 비활성 | ❌ | 정상 동작, 오류 아님 |

- 성공 시 error row **delete는 `recordUpload`와 같은 흐름에서** (가능하면 같은
  트랜잭션으로). 따로 하면 그 사이 크래시가 "ledger에도 있고 error에도 있는" 모순 행을
  남기고, UI는 실제로는 올라간 사진을 실패로 표시하게 된다. 방어를 겹으로: UI/조회 쿼리도
  **ledger 행이 있으면 error 행을 무시**하는 것을 원칙으로 한다.
- 큐잉 전 필터는 ledger만 보던 것에서 바뀌지 않는다 — 실패 기록이 있어도 재큐잉은 허용
  (그게 복구 경로니까). 이것은 **Phase 1에 한정된 의도적 입장**이다: Phase 2가 터미널
  분류를 들여오면 이 쿼리에 조건부 anti-join이 추가된다(전면 재작성 아님).
- 이것만 있어도 "무엇이 왜 실패했나"를 SQL 한 줄로 답할 수 있게 된다.

### Phase 2: 터미널 실패를 구분하고, 조용한 낭비를 멈춘다

- 에러 분류기로 `storageQuotaExceeded`를 `quota_exceeded`로 태깅. **주의: 기존
  `isInvalidGrant`를 손보는 게 아니라 새 접근자다** — invalid_grant는
  `error.response.data.error`(문자열)에 있지만, quota는
  `error.response.data.error.errors[].reason`(중첩 배열)에 있다. 모양이 다르니 대칭을
  가정하지 말 것 (2차 리뷰 확인).
- **재시도 낭비는 백필 레벨만이 아니다.** 현재 retryConfig는 모든 403을 5회 재시도한다
  — quota 403도 매 작업마다 5회씩 태운다. `shouldRetry` 콜백을 추가해
  `storageQuotaExceeded`인 403은 즉시 실패시킨다(rate-limit 403은 계속 재시도).
- **quota 실패가 기록된 사용자는 백필/자동 큐잉에서 제외**하고, 설정 페이지에 "Drive 용량이
  가득 차 업로드가 중단됨 — 공간 확보 후 재개" 배너 + **재개 버튼**(에러 기록 삭제 →
  다음 백필에 포함).
- 파일-단위 터미널(원본 없음)은 지금처럼 skip 유지하되 에러 테이블에는 남긴다.

### Phase 3: 보이게 한다

- **설정 페이지**: 연결 상태 옆에 요약 — "업로드됨 N / 실패 M". M>0이면 펼쳐서 실패 목록
  (썸네일 + 사유 + 시각), "전체 재시도" 버튼(해당 자산 재큐잉). 이 버튼이 §1의 "수동
  트리거 전까지 대기" 문제를 실질적으로 닫는다.
- **앨범 페이지**: `GET /google-drive/albums/:id/status` → `{ total, uploaded, failed }`.
  의미를 명확히: ledger는 앨범이 아니라 `(userId, assetId)` 단위이므로 **"uploaded" =
  앨범 소유자의 ledger 행이 있는 자산**, `pending = total − uploaded − failed`. 동기화
  버튼 옆에 "n/m 동기화됨" 카운트만 — 자산마다 뱃지는 타임라인 렌더링을 건드려야 해서
  비용 대비 효과가 낮음.
- **인앱 알림**: 발화 조건은 좁게 — ① quota로 업로드 중단, ② `invalid_grant`로 자동 연결
  해제. 개별 사진 실패마다 알리는 건 소음이므로 하지 않는다. 두 가지 구현 원칙:
  - **상태 전이당 1회.** error 테이블의 분류가 터미널로 *바뀌는 순간*에만 발화. 안 그러면
    백필을 다시 돌릴 때마다 같은 알림이 반복된다.
  - enum(`NotificationType`)에 값을 추가하면 SDK 재생성이 딸려온다 — `Custom` 타입으로
    충분하면 그쪽을 우선 검토.

### 순서와 규모

Phase 1이 나머지의 전제라 먼저. 1+2가 한 덩어리(마이그레이션 1 + 워커 catch 확장 + 백필
필터 + 설정 UI 배너)로 적당한 크기고, Phase 3는 그 위에 UI만 얹으면 된다.

## 4. 미리 정해 둘 판단들

1. **실패 기록의 보존 기간** — 성공 시 삭제 외에, 오래된 기록을 청소할지. 제안: 안 함
   (테이블이 커질 실질 경로가 없음; 실패는 성공하거나 사용자가 지우거나).
2. **재시도 횟수 상한** — `attempts`가 계속 쌓이는 사진(매번 unknown 실패)을 몇 회 이후
   터미널로 취급할지. 제안: 상한 없이 두되 설정 UI에서 attempts를 보여줘 사용자가 판단.
   **다만 이건 해결이 아니라 알려진 잔여 문제로 기록해 둔다**: unknown 실패 자산은 ledger에도
   못 들어가고 터미널도 아니어서 백필마다 영원히 재시도된다 — quota에서 없애려는 것과 같은
   종류의 조용한 낭비가 작은 규모로 남는 것. 2인 서버에선 감수, 규모가 커지면 상한 도입.
3. **알림 채널** — 인앱만 할지 이메일(immich SMTP 설정이 있으면)까지 갈지. 제안: 인앱만
   먼저. 이 서버의 사용자 2명은 어차피 UI를 본다.

## 5. 계획과 별개인 코드 후속 과제 (2차 리뷰에서 확정)

Phase 1~3와 독립적으로, 업로드 코드를 다음에 건드릴 때 함께:

1. **시도마다 스트림 재생성** (R2의 근본 해결) — 지금의 크기 검증은 잘린 재전송을
   *탐지*하지, *방지*하지 못한다. 재시도 시 `fs.ReadStream`을 새로 여는 구조(스트림 팩토리
   또는 소형 파일 버퍼링)로 바꾸면 위험 자체가 사라지고, 그때 "size 부재 → 실패"라는 가장
   보수적인 판정을 "허용"으로 완화할 수 있다(유일한 거짓-실패 경로 제거). 크기 검증은 다른
   손상도 잡는 값싼 백스톱이므로 그대로 유지.
2. **R3 skip 범위 재조정** — 현재는 읽기 오류 전부 skip. error 테이블이 생긴 뒤에는
   ENOENT(파일이 정말 없음)만 skip으로 남기고, EACCES/EIO 같은 일시적일 수 있는 오류는
   "기록 + 실패"(R1 덕에 재시도 가능)로 분리하는 게 더 정직하다. **테이블 이전에는 손대지
   않는다** — 지금은 skip과 fail의 결과가 사실상 같아서 바꿀 이유가 없다.
3. **운영 관찰 항목** — 라이브 1주 후 로그에서 "an unknown number of bytes"(size 부재
   throw)를 grep. 한 번이라도 잡히면 "Drive는 바이너리에 항상 size를 준다"는 경험적 전제가
   깨졌다는 신호이므로 1번을 앞당긴다.
