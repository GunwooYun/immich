배포 완료된 구글드라이브 앨범 동기화(v3.1.0 기반, 2026-08-15 운영 투입) 위에 쌓을 다음

아직 없고, 각 Wave가 끝날 때마다 코드 리뷰를 따로 요청할 예정.

## 0. 배경 — 이 파이프라인에서 Drive는 경유지다

```
immich 모바일 → 랩탑 immich → Google Drive → Pixel 1XL(DriveSync가 다운로드)
                                                → Google Photos (원본 무료 업로드)
```

Drive는 최종 저장소가 아니라 **Pixel로 가는 중계 버퍼**다. 이 사실이 설계 전반을 지배한다:

1. **quota 소진은 "만약"이 아니라 "언제"다.** 무료 15GB에 원본(동영상 포함)이 쌓인다.
   Pixel이 옮긴 뒤 Drive 쪽 파일을 지우면 사용량이 "아직 안 옮긴 분량"으로 유지되지만,
   그 청소가 늦어지는 순간 차오른다.
2. **파일 삭제는 정상 운영이다.** Drive에서 파일이 사라져도 ledger가 "업로드됨"을
   기억하므로 재업로드하지 않는다 — 경유지 모델에 정확히 맞는 동작이고, 바꾸지 않는다.
   단 **폴더 자체를 지우면** 이후 업로드가 전부 404로 실패한다(파일만 비워야 함).
3. **"어디까지 갔나"의 가시성이 파이프라인 감시의 전부다.** 정체는 immich→Drive 구간에서만
   우리가 관측할 수 있다.

## 1. 현재 상태 — 이미 되어 있는 것 / 비어 있는 것

**되어 있음**: 자동 업로드(앨범 추가 시)·수동 동기화(앨범 버튼)·관리자 백필의 3개 트리거,
중복 방지 3겹(큐잉 전 ledger 필터 → BullMQ jobId dedup → 워커 재확인), 잘린 업로드 검증
(크기 대조 + 부분 파일 삭제), `invalid_grant` 자동 해제, 원본 유실 skip, fd 누수 방지,
실패 작업의 재큐잉 가능성(R1: `removeOnFail: true`), 폴더 선택 Picker.

**비어 있음**: 실패의 **기록**(서버 로그뿐), 실패의 **표시**(R1의 대가로 Jobs 패널 카운트도
없음), quota의 **분류**(일반 403으로 취급 → 백필마다 잔여 전체가 5회씩 재시도·실패),
업로드 진행의 **가시성**, 선택적 업로드, 자동 업로드 끄기.

실제 사고 사례가 근거다: 배포 당일 `invalid_client` 실패가 화면에는 "unable to connect"
로만 보였고 원인은 서버 로그에만 있었다.

## 2. Wave 1 — 실패 처리 기반 (선행 문서 Phase 1+2의 구현)

**왜 최우선인가**: 서희카메라 1,809장 + 인화사진 63장의 대량 동기화가 남아 있다. quota
보호 없이 돌리다 용량이 차면 현재 코드는 잔여 수백 장을 장당 5회씩 조용히 재시도하며
실패한다. 방어막을 치고 나서 큰 동기화를 하는 순서가 안전하다.

### 2.1 실패 기록 테이블

```
google_drive_upload_error
  userId       uuid  FK user  ON DELETE CASCADE   ┐
  assetId      uuid  FK asset ON DELETE CASCADE   ┘ PK (userId, assetId)
  error        varchar   -- 분류 코드: quota_exceeded | folder_missing | size_mismatch
                          --            | source_unreadable | revoked | rate_limited | unknown
  detail       varchar   -- 원본 메시지 (512자 절단)
  attempts     int
  lastFailedAt timestamptz
```

ledger(`google_drive_upload`)와 **반대 극성**: 행 존재 = 실패 상태, 성공 시 삭제.

**기록 지점 — catch 하나가 아니다** (2차 리뷰가 잡은 함정, 그대로 구현):

| 경로 | 기록 | 분류 |
|---|---|---|
| catch: 재시도 소진(429/5xx), 크기 불일치, unknown | ✅ upsert | rate_limited / size_mismatch / unknown |
| catch: 폴더 404 | ✅ upsert | folder_missing |
| skip: 원본 파일 없음/못 읽음 (`return 'skipped'`) | ✅ upsert | source_unreadable |
| skip: `invalid_grant` → 자격증명 삭제 | ✅ upsert | revoked |
| skip: 자산 삭제/휴지통 | ❌ | 정상 동작 |
| skip: 미연결 / 기능 비활성 / ledger 존재 | ❌ | 정상 동작 |

**정합성 규칙 2개** (2차 리뷰 반영):
- 성공 시 error 행 삭제는 `recordUpload`와 **같은 흐름에서**(동일 트랜잭션 지향).
- 모든 조회는 **ledger 행이 있으면 error 행을 무시**한다 — 크래시 타이밍에 따라 둘 다
  존재할 수 있고, 그때 진실은 ledger다.
- 큐잉 전 필터는 Wave 1에서는 ledger만 본다(실패 기록이 있어도 재큐잉 허용 — 그게 복구
  경로). §2.2의 터미널 분류가 들어오면 조건부 anti-join이 추가된다.

### 2.2 quota 분류와 차단

- **분류기는 새 접근자다**: `invalid_grant`는 `error.response.data.error`(문자열)에 있지만
  quota는 `error.response.data.error.errors[].reason === 'storageQuotaExceeded'`(중첩
  배열)에 있다. 기존 `isInvalidGrant`를 손대지 않고 별도 함수로.
- **`shouldRetry` 콜백 추가**: 현재 retryConfig는 모든 403을 5회 재시도한다. quota 403은
  즉시 실패시키고(rate-limit 403은 유지), 같은 자리에서 `folder_missing`(404)도 즉시
  실패로 분류한다.
- **백오프는 검증 완료**: gaxios 6.7.1 소스 확인 결과 `retryDelay`는 첫 재시도에만 쓰이고
  이후는 지수 증가한다(multiplier 2 기본: 약 1000→500→1500→3500→7500ms). 지터는 없지만
  동시성 5에서는 수용 가능 — 코드 변경 불필요, 사실만 기록해 둔다.
- **백필/자동 큐잉에서 quota 상태 사용자 제외**: `streamPendingUploads`에 "터미널 분류의
  error 행이 있는 사용자 제외" anti-join. 개별 자산 단위가 아니라 **사용자 단위**로
  멈추는 이유: quota는 자산의 속성이 아니라 계정의 상태다.
- **워커 입구 게이트 (로드맵 리뷰 Gap A, must-fix)**: 백필은 스트림을 다 돌려 잔여 전체를
  큐에 넣은 뒤에야 첫 실패가 기록된다 — anti-join은 *다음* 백필만 보호한다. 그래서
  `uploadAsset` 입구(자격증명 확인 직후)에서 "이 사용자에게 터미널 분류 error 행이
  있는가"를 조회해 있으면 즉시 skip한다(에러 행 추가 기록 없음 — 해당 자산들은 pending으로
  남아 재개 시 재큐잉된다). 1,809장 동기화 중 quota가 터지는 바로 그 시나리오에서
  **Drive 호출 1,809회 → 1회 + 값싼 skip 1,808회**가 된다.
- **재개 경로 (Gap C 반영)**: 설정 페이지 배너 "Drive 용량 부족으로 업로드 중단됨" +
  [용량 확인 후 재개] 버튼 → quota 분류 error 행 삭제 **+ 그 사용자 범위의 백필을 즉시
  큐잉**. "다음 트리거에서 재개"는 며칠 뒤일 수 있다 — 방금 용량을 비우고 버튼을 누른
  사용자는 지금 시작되기를 기대한다. 재개 직후 또 quota가 터지면 다시 차단되는 자연
  수렴으로 레이스는 충분히 흡수된다(리뷰 판정 동일).

### 2.3 알림 (선행 문서 Phase 3에서 이동)

Wave 1 서버 작업에 얹는 게 자연스러워 여기로 옮긴다. `NotificationType.Custom` 사용
(enum 추가는 SDK 재생성이 딸려오므로 회피), 발화는 **상태 전이당 1회** — error 테이블에
해당 분류가 **처음 생길 때만**: ① quota로 중단될 때, ② `invalid_grant`로 자동 해제될 때.
개별 사진 실패는 알리지 않는다(소음).

"처음"의 판정은 원자적이어야 한다(Gap D): 동시성 5에서 다섯 워커가 동시에 "행 없음"을
읽고 각자 발화하면 배너가 5개 뜬다. upsert의 `INSERT … ON CONFLICT` 결과로 삽입/갱신을
구분해(xmax=0 또는 RETURNING으로 판별) 삽입된 워커만 알림을 만든다.

### 2.4 테스트 계획

- 기록 지점 표의 각 행마다 1개 (기록되는 5경로 + 기록 안 되는 3경로)
- quota 403 → shouldRetry가 즉시 실패시키는지 / rate-limit 403은 재시도하는지
- 성공 시 error 행 삭제, "ledger 우선" 조회 규칙
- 백필이 quota 사용자를 건너뛰는지 (medium 또는 mock 스트림)
- **입구 게이트**: quota 행이 있는 사용자의 후속 작업이 Drive 호출 없이 skip되는지
- **재개**: 버튼 → error 행 삭제 + 해당 사용자 백필 큐잉이 함께 일어나는지
- 알림이 전이당 1회인지 (두 번째 quota 실패에 재발화 없음, 동시 삽입 경합 포함)

**규모**: 마이그레이션 1, 리포지토리 메서드 4~5, 워커 수정, 알림, 배너 UI. ~1일.

## 3. Wave 2 — 앨범 Drive 드롭다운 메뉴

앨범 상단의 Drive 아이콘을 **즉시 실행 버튼 → 메뉴**로 바꾼다. 큰 동작(전체 업로드)이
클릭 한 번에 나가는 현재 UX의 교정이면서, 관련 기능의 집이 된다.

```
┌────────────────────────────────────┐
│ ▶  지금 업로드          1,809장 남음 │
│ ⟳  동기화 진행 중  123/1,809        │   ← Wave 3에서 활성화
│    ▓▓▓▓▓░░░░░░░░░░░  6%            │
│ ────────────────────────────────── │
│ ☁  Drive 저장용량                   │
│    ▓▓▓▓▓▓▓▓▓▓▓▓░░░  12.3/15 GB    │   ← 80% 노랑 / 95% 빨강
│ ────────────────────────────────── │
│ ⧉  Google Drive에서 열기        ↗  │
└────────────────────────────────────┘
```

### 3.1 신규 엔드포인트 2개

**`GET /google-drive/albums/:id/status`** → `{ total, uploaded, failed, pending }`
- 의미 정의(2차 리뷰 반영): ledger는 앨범이 아니라 `(userId, assetId)` 단위이므로
  **uploaded = 앨범 소유자의 ledger 행이 있는 자산 수**, failed = 소유자의 error 행이
  있는 자산 수(ledger 우선 규칙 적용), `pending = total − uploaded − failed`.
- **`deletedAt` 필터는 세 카운트 모두에** (Gap B): total에만 걸면 "업로드 후 휴지통행"
  자산이 uploaded에는 남아 pending이 음수가 된다. 하드 삭제는 ledger FK CASCADE로 행이
  사라지지만 **휴지통은 소프트 삭제라 행이 남는다** — 이 필터가 카운트 정합성의 전부다.
- 권한: 앨범 읽기 권한. 집계는 항상 소유자 기준. 공유 사용자 화면에는 **"[소유자]의
  Drive에 백업됨 — N/M"** 으로 라벨링해 자기 것으로 오독하지 않게 한다(Q5 판정 반영).

**`GET /google-drive/me/status`** → `{ pending, failed }` (Gap E, Wave 2에서 함께 설계)
- Wave 3의 진행 카드와 Wave 4의 선택 업로드가 공유할 **사용자 단위** 소스. 앨범
  엔드포인트는 앨범·소유자 범위라 선택 업로드(앨범 비종속, 본인 Drive행)를 측정하지
  못한다 — 나중에 카드 데이터 모델을 뜯는 것보다 지금 엔드포인트를 나란히 설계한다.
- pending 정의: 본인이 소유한 앨범들의 백필 대상 집합(= `streamPendingUploads`와 같은
  조건의 카운트판). 앨범 밖 자산의 선택 업로드는 클라이언트가 선택 id를 이미 알고
  있으므로, 카드가 그 id 집합의 완료 수를 함께 표시하는 것으로 보완한다.

**`GET /google-drive/storage`** → `{ limitBytes | null, usageBytes, usageInDriveBytes }`
- Drive `about.get(fields: 'storageQuota')` — **`drive.file` 스코프로 호출 가능**(About
  리소스의 허용 스코프에 포함). 서버가 저장된 refresh token으로 조회하므로 브라우저에
  토큰이 가지 않는다.
- 무제한 계정은 `limit`이 없다 → `limitBytes: null`이면 게이지 대신 사용량 숫자만 표시.
- **사용자당 60초 서버 캐시**: 메뉴를 여닫을 때마다 구글을 때리지 않기 위해. 이 규모에서
  더 정교한 캐시는 과잉.
- 조회 대상은 **인증된 사용자 본인의 Drive**다(소유자의 것이 아님 — 메뉴가 소유자에게만
  보이므로 실질적으로 동일 인물).
- **`invalid_grant` 처리**: 토큰이 폐기된 사용자의 조회는 500이 아니라 "연결 끊김" 형태로
  반환한다(`uploadAsset`과 같은 분류 재사용). 엔드포인트 계약에 명시.
- **구현 착수 전 30초 실검증**(리뷰 권고): 실제 저장된 refresh token으로
  `about.get({fields:'storageQuota'})`를 1회 호출해 응답을 확인한다. 전제가 틀리면
  전 사용자 재동의가 필요해지는 가정이므로, 보험 치고 싸다.

### 3.2 UI 규칙

- 메뉴는 **앨범 소유자에게만** 표시(동기화가 소유자 전용인 것과 일관).
- 미연결 상태면 메뉴 대신 "Google Drive 연결하기" 항목 하나 → 설정 페이지로.
- Drive 열기: `https://drive.google.com/drive/folders/{folderId}` 새 탭. 폴더 미설정이면
  Drive 루트.
- 게이지 색: ~80% 기본, 80~95% 경고(노랑), 95%+ 위험(빨강). Wave 1의 quota 차단과 색
  기준을 공유한다 — 게이지가 빨강이 되기 전에 사용자가 Pixel 청소를 하게 만드는 것이
  이 게이지의 존재 이유.
- **사진 상세 패널**에 한 줄: "Google Drive — 업로드됨 / 대기 / 실패(사유)". 상세를 열
  때 1회 조회. 타임라인 격자 뱃지는 하지 않는다(수천 장 렌더링 경로에 조회를 끼우는
  비용 대비 정보 가치 낮음 — 상세 패널 + 앨범 카운트로 같은 질문에 답함).

**규모**: 엔드포인트 2, 캐시, 드롭다운 컴포넌트, 상세 패널 한 줄, SDK 재생성. ~1일.

## 4. Wave 3 — 업로드 진행 표시

### 4.1 방식: 폴링, 웹소켓 아님

3~5초 간격으로 Wave 2의 status 엔드포인트를 재사용한다. 근거:
- 업로드는 서버 백그라운드 작업이라 페이지 새로고침과 무관하게 진행된다. "지금 상태를
  물어보는" 폴링이 정직한 소스다.
- immich 웹소켓에 커스텀 이벤트를 얹으면 이벤트 타입·SDK·모바일까지 배선이 번진다.
  가족 서버 규모에서 3초 지연은 체감 불가. 웹소켓은 필요해지면 그때(선택 업그레이드).
- 탭이 백그라운드면 폴링 중지(Page Visibility API), 카운트 변화가 없는 폴링이 5회
  연속이면 간격을 10초로 늘린다.

### 4.2 표현: immich의 업로드 패널 문법 재사용

브라우저 업로드 때 뜨는 우하단 카드와 같은 시각 언어:

```
┌──────────────────────────────┐
│ ☁ Google Drive 동기화 중      │
│ ▓▓▓▓▓▓░░░░░░░░  123/1,809    │
│                    [접기 ▾]   │
└──────────────────────────────┘
```

- 완료 시 체크마크 3초 → 사라짐. 실패 잔존 시 "N장 실패 — 보기"로 남고 클릭하면 설정
  페이지의 실패 목록으로.
- 드롭다운 메뉴 안의 진행 바와 **같은 폴링 스토어를 공유**(중복 폴링 없음).
- **카드는 이 탭에서 사용자가 동기화를 시작했을 때만 자동 등장**한다. 백그라운드
  자동 업로드(앨범 추가)만으로 카드가 불쑥 뜨면 놀람이 된다 — 그 경우 진행은 메뉴를
  열어야 보인다. (이건 UX 판단이며 §8-4에서 리뷰를 청한다.)

**규모**: 폴링 스토어 + 카드 컴포넌트 + 메뉴 연동. ~반나절.

## 5. Wave 4 — 선택 업로드 + autoSync 토글

### 5.1 선택한 사진만 업로드

- **의미**: 선택 업로드는 앨범 동기화("소유자의 Drive로")와 달리 **누르는 사람 본인의
  Drive로** 간다. "내가 고른 걸 내 백업으로"라는 다른 의도이고, 공유 앨범에서 각자가
  자기 몫을 백업하는 시나리오를 자연스럽게 연다. ledger가 사용자별이라 중복 관리는
  그대로 동작한다.
- **권한은 다운로드와 동급으로 게이트** (Q1 판정): 보고 내려받을 수 있으면 이미 반출
  가능하므로 본인 Drive 업로드는 새 신뢰 경계가 아니다. 단 읽기/썸네일 권한이 아니라
  **실제 다운로드 권한 검사와 같은 경로**를 태워, 향후 "다운로드 금지" 플래그가 생기면
  선택 업로드가 자동으로 상속하게 한다.
- 서버: `POST /google-drive/assets/sync`, body `BulkIdsDto`. 본인 연결 필수(아니면 400),
  위 권한 검사 후 `queueGoogleDriveUploads(본인 id)` 재사용.
- 웹: 다중선택 액션 메뉴에 "Google Drive에 업로드" + "n장이 대기열에 추가됨" 토스트.
  Wave 3의 진행 카드가 이 트리거에도 반응.

### 5.2 autoSync 토글

- `user_google_drive.autoSync boolean NOT NULL DEFAULT true` (마이그레이션 1).
- **자동 경로에서만 검사**: `queueGoogleDriveUploads`가 이미 googleDrive 리포지토리를
  받으므로 그 안에서 `getCredentials(ownerId)`를 조회해 연결 여부 + autoSync를 함께
  확인한다. 부수 효과로 **미연결 소유자의 no-op 작업을 큐에 넣지 않게 된다**(현재는
  큐잉 후 워커가 skip). 비용은 앨범 추가당 PK 조회 1회 — §8-2에서 리뷰를 청한다.
- 수동 동기화·백필·선택 업로드는 토글을 **무시**한다(명시적 의사).
- 설정 페이지에 토글 + 설명 한 줄.

**규모**: 엔드포인트 1, 마이그레이션 1, 선택 액션, 토글 UI. ~1일.

## 6. 일부러 하지 않는 것

| 항목 | 이유 |
|---|---|
| 타임라인 격자 사진별 뱃지 | 수천 장 렌더링 경로 비용. 상세 패널+카운트로 대체 |
| 웹소켓 실시간 이벤트 | 규모 대비 배선 과잉. 폴링으로 충분, 필요 시 업그레이드 |
| 사진별 실패 알림 | 소음. 알림은 quota 중단·연결 해제 두 가지만 |
| 이메일 알림 | 사용자 2명이 어차피 UI를 봄. 인앱만 |
| error 행 보존기간 청소 | 성공 시 삭제 외 증식 경로 없음 |
| Drive 쪽 파일 상태 역추적 | 경유지 모델에서 삭제는 정상. ledger가 진실 |

## 7. 공통 사항

- **Wave마다**: 유닛 테스트(§2.4 수준의 밀도), `tsc`/`eslint`/전체 스위트, OpenAPI·SQL
  재생성, i18n 정렬 규칙 준수, 상세 커밋 메시지, Wave 종료 시 코드 리뷰 요청.
- **배포**: 검증된 경로 재사용 — 데스크탑 빌드 → `docker save | ssh | load` → compose
  재기동. Wave 1 배포 후 남은 앨범 대량 동기화를 실행한다(방어막 확보 후).
- **대량 동기화 전 사전 점검**(리뷰의 pre-flight 제안을 운영 절차로 흡수): 잔여 자산의
  바이트 합(DB의 exif fileSizeInByte 집계)과 Drive 잔여 용량을 비교해 "끝까지 갈 수
  있는가"를 돌리기 전에 확인한다. Wave 2의 용량 엔드포인트가 생기면 UI로 승격.
- **마이그레이션 2개**(Wave 1 error 테이블, Wave 4 autoSync)는 각 Wave에서 독립 적용.
  기존 5개와 마찬가지로 스쿼시하지 않는다.

## 8. 리뷰어에게 물었던 질문 — 판정 완료 (`dev-docs/review/google-drive/review/google-drive-roadmap-20260815-1511-review.md`, 2026-08-15)

6개 전부 답을 받았고 본문에 반영했다. 요약: ①다운로드 동급+권한 경로 공유(§5.1) ②util 내부 조회 지지(§5.2) ③자연 수렴 충분하되 재개는 재큐잉 필수(§2.2) ④수용, 새로고침 유실 엣지 문서화(§4.2) ⑤소유자 기준 유지+라벨링(§3.1) ⑥전제 성립, 착수 전 실검증(§3.1). 원 질문은 기록으로 유지:

1. **선택 업로드의 권한 수준** (§5.1): 공유받은 자산을 자기 Drive로 올리는 것은 실질적
   데이터 반출이다. 다운로드 권한과 동급으로 취급하면 되는가, 아니면 자기 소유 자산으로
   제한해야 하는가? (현 계획: 다운로드와 동급 — 볼 수 있고 받을 수 있으면 내보낼 수 있다)
2. **autoSync 검사 위치** (§5.2): `queueGoogleDriveUploads` 내부에서 credentials 조회로
   통합하는 안 — 앨범 추가마다 PK 조회 1회 추가가 수용 가능한가? 대안(호출부에서 조회해
   파라미터로 전달)이 더 나은가?
3. **quota 재개 버튼의 레이스** (§2.2): 재개(error 행 삭제)와 동시에 진행 중이던 실패
   기록이 다시 쓰이는 경합 — "재개 후 첫 실패에서 다시 차단"이라는 자연 수렴으로 충분한가?
4. **진행 카드의 등장 조건** (§4.2): 사용자가 시작한 동기화에만 자동 등장, 백그라운드
   자동 업로드는 메뉴에서만 확인 — 맞는 판단인가, 아니면 pending>0이면 항상 보여야 하는가?
5. **status 집계의 소유자 고정** (§3.1): 공유 사용자가 보는 카운트도 소유자 기준 —
   "이 앨범이 소유자의 Drive에 얼마나 백업됐나"로 일관되지만, 헷갈릴 여지는 없는가?
6. **`about.get`의 스코프 전제** (§3.1): `drive.file`로 storageQuota 조회가 가능하다는
   전제 — 반례를 아는가? (틀리면 게이지 기능 전체가 스코프 확장을 요구하게 됨)
