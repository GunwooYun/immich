# 개발 환경 이해하기 — Docker, Dev Container, 그리고 immich

immich를 고치려면 **똑같은 immich가 두 벌** 돌아간다는 사실부터 이해해야 한다. 하나는
개발용(데스크탑), 하나는 운영용(랩탑). 둘은 목적도, 만들어지는 방식도, 다루는 법도 다르다.
이 문서를 쓴 이유는 그 둘을 헷갈려서 실제로 시간을 여러 번 날렸기 때문이다.

---

## 1. Docker — "프로그램 + 그게 필요로 하는 모든 것"을 한 상자에

immich는 혼자 못 돈다. 데이터베이스(PostgreSQL), 캐시(Redis), 얼굴 인식용 파이썬 서비스가
같이 있어야 하고, 각각이 특정 버전을 요구한다. 이걸 컴퓨터에 직접 설치하면
"내 PC에서는 되는데요"가 시작된다.

Docker는 그 각각을 **격리된 상자(컨테이너)** 에 넣는다.

```
      [내 컴퓨터]
  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐
  │ immich  │ │postgres │ │  redis  │ │   ML    │   ← 컨테이너 4개
  │ 서버    │ │  14     │ │    9    │ │ 파이썬  │      각자 격리됨
  └─────────┘ └─────────┘ └─────────┘ └─────────┘
       └───────────┴───────────┴───────────┘
              서로 네트워크로만 통신
```

핵심 용어 세 개면 충분하다:

| 용어 | 뜻 | 비유 |
|---|---|---|
| **이미지(image)** | 실행에 필요한 게 다 들어간 **읽기 전용 스냅샷** | 설치 CD |
| **컨테이너(container)** | 이미지를 **실행한 것** | CD로 설치해 돌아가는 프로그램 |
| **볼륨(volume)/마운트** | 컨테이너 **밖의 파일을 안에서 보이게** 연결 | 외장하드 꽂기 |

컨테이너는 지웠다 다시 만들어도 이미지만 있으면 똑같이 복원된다. 그래서 **컨테이너 안의
변경은 사라진다** — 사진과 DB가 볼륨으로 바깥에 나와 있어야 하는 이유다.

**`docker compose`** 는 이 여러 컨테이너를 YAML 파일 하나로 묶어 한 번에 켜고 끄는 도구다.
`docker-compose.yml`이 그 파일이고, `docker compose up -d`가 "다 켜라"다.

## 2. Dev Container — 개발 도구까지 상자 안에 넣기

여기까지는 "프로그램을 돌리는" 이야기였다. **개발**은 요구가 하나 더 있다:
코드를 고치면 **즉시 반영**되어야 한다. 고칠 때마다 이미지를 다시 만들면(5~10분) 아무도
개발을 못 한다.

Dev Container는 두 가지를 한다:

1. **소스 코드를 컨테이너 안으로 마운트한다.** 컨테이너 안에 코드를 복사해 넣는 게 아니라,
   내 디스크의 폴더를 컨테이너가 들여다보게 한다. 내가 파일을 저장하면 컨테이너 안에서도
   즉시 바뀐 파일이 보인다.
2. **개발 도구(Node, pnpm, 컴파일러)를 컨테이너 안에 넣는다.** 내 PC에 Node 버전을 맞춰
   설치할 필요가 없다.

```
  [내 디스크]                      [컨테이너 안]
  ~/workspace/immich/server/src ──마운트──▶ /usr/src/app/server/src
        │                                        │
        │ 파일 저장                               │ nest --watch 가 변경 감지
        └────────────────────────────────────────▶ 자동 재시작 (수 초)
```

VS Code의 "Dev Containers" 확장이 이걸 자동화한다. `.devcontainer/devcontainer.json`이
설계도이고, 창을 열면 VS Code가 컨테이너를 띄운 뒤 **자기 자신도 컨테이너 안으로 들어간다**
— 그래서 터미널을 열면 내 PC가 아니라 컨테이너 안의 셸이 나온다.

## 3. immich의 개발 환경 — 컨테이너 6개

`docker/docker-compose.dev.yml`이 정의한다. 운영보다 컨테이너가 더 많다.

```
 ┌──────────────────────────────────────────────────────────┐
 │  immich-web    (Vite)      :3000   ← 브라우저가 보는 화면 │
 │      │ API 호출                                           │
 │      ▼                                                    │
 │  immich-server (Nest)      :2283   ← 백엔드 + 워커        │
 │      │            │                                       │
 │      ▼            ▼                                       │
 │  database     redis        immich-machine-learning        │
 │  (postgres)   (valkey)     (얼굴/사물 인식)               │
 │                                                           │
 │  immich-init / immich-app-base  ← 준비용, 금방 끝남       │
 └──────────────────────────────────────────────────────────┘
```

- **immich-web(:3000)** — 개발 중에는 프론트엔드가 **별도 컨테이너**에서 Vite로 돈다.
  `.svelte` 파일을 저장하면 브라우저가 알아서 갱신된다.
- **immich-server(:2283)** — 백엔드 API와 백그라운드 워커. `nest start --watch`로 돌아서
  `.ts`를 저장하면 몇 초 뒤 재시작한다.
- **나머지**는 운영과 같은 공식 이미지를 그대로 쓴다.

### 운영과 무엇이 다른가 — 이게 제일 중요하다

| | 개발 (데스크탑) | 운영 (랩탑) |
|---|---|---|
| 소스 코드 | 디스크에서 **마운트** | 이미지 안에 **컴파일되어 박힘** |
| 프론트엔드 | **별도 컨테이너**(Vite, :3000) | 서버 이미지 **안에 포함** (:2283) |
| 코드 수정 시 | 저장하면 몇 초 후 반영 | 이미지 재빌드 → 전송 → 재기동 |
| 컨테이너 수 | 6개 | 4개 |
| 이미지 출처 | 소스에서 빌드 | `docker load`로 받은 것 |

**운영에는 :3000이 없다.** 프론트엔드가 서버 이미지에 말려 들어가 `:2283`이 화면과 API를
모두 낸다(`server/Dockerfile`이 web을 빌드해 `/build/www`에 넣는다). 그래서 랩탑에서는
`http://192.168.50.211:2283` 하나만 쓴다.

## 4. 이 프로젝트의 전체 그림

```
 [데스크탑 WSL] ─── 개발 ───────────────────────────────┐
   Dev Container 6개                                    │
   코드 수정 → 즉시 반영 → localhost:3000 에서 확인     │
                                                        │
   ✔ 테스트 통과 후                                     │
   docker build ──▶ immich-server:3.1.0-gdrive (3.25GB) │
                          │                             │
                          │ docker save | ssh | load    │
                          ▼                             │
 [랩탑 192.168.50.211] ─ 운영 ─────────────────────────┘
   컨테이너 4개, 사진 6,500장
   docker compose up -d → 마이그레이션 자동 적용
```

배포에서 우리가 바꾸는 것은 랩탑 `docker-compose.yml`의 **`image:` 한 줄뿐**이다.
나머지 3개 컨테이너는 공식 이미지를 그대로 쓴다.

## 5. 자주 하는 일

```bash
# ── 개발 시작 ──
# VS Code에서 immich 폴더 열기 → "Reopen in Container" → 자동으로 6개 컨테이너 기동
# 브라우저: http://localhost:3000

# ── 컨테이너 상태 보기 ──
docker ps                      # 도는 것
docker ps -a                   # 멈춘 것까지
docker logs immich_server -f   # 로그 실시간

# ── 개발 환경 끄기 ──
docker stop immich_server      # 하나만
cd docker && docker compose -f docker-compose.dev.yml down   # 전부

# ── 운영(랩탑) 보기 ──
ssh gwyun@192.168.50.211 'docker ps'
```

## 6. 실제로 밟았던 함정

이 문서를 쓴 진짜 이유다. 전부 "개발과 운영을 헷갈려서" 생긴 일이다.

### 포트 2283을 두고 싸운다

데스크탑 Dev Container도 :2283, 랩탑 운영도 :2283. 랩탑에 붙으려고 SSH 터널을 뚫었는데
데스크탑 컨테이너가 켜져 있으면 **브라우저가 랩탑이 아니라 그 컨테이너에 붙는다.**
증상은 `ERR_EMPTY_RESPONSE`인데, 이 메시지는 원인을 전혀 안 가리킨다. 두 번 겪었다.

```bash
ss -tln | grep :2283            # 터널 쓰기 전 비어 있어야 함
docker ps | grep immich_server  # 있으면 docker stop
```

### 컨테이너가 만든 파일은 root 소유다

Dev Container는 root로 돈다(`remoteUser: root`). 그 안에서 빌드하면 `server/dist`의 파일이
**내 계정이 아니라 root 소유**로 생긴다. 그 다음 호스트에서 빌드하면 `EACCES`로 막힌다.

```bash
docker stop immich_server && rm -rf server/dist   # 컨테이너 멈추고 지우고 다시
```

컨테이너가 도는 동안은 watch가 계속 파일을 다시 만들어서, **먼저 멈추지 않으면 무한 반복**
한다. 이것도 겪었다.

### `dist`는 알아서 안 지워진다

`nest build`는 예전 산출물을 지우지 않는다. 그래서 **삭제한 마이그레이션이 되살아난** 적이
있다 — 소스에서는 지웠는데 `dist`에 컴파일된 게 남아 실행된 것이다. 이상하면 `dist` 삭제.

### Dev Container가 저절로 되살아난다

VS Code의 immich-dev 창이 열려 있으면 `docker stop`으로 꺼도 다시 켜진다. 터널을 쓰는 동안은
**그 창을 닫아야** 한다.
