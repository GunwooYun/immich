## 1. 왜 필요한가 — 현재 모델이 표현하지 못하는 것

현재 규칙은 코드에 박혀 있다: **"업로드는 앨범 소유자의 드라이브로 간다."**
(`album.service.ts`의 `getAlbumOwnerId`, `streamPendingUploads`의 `album_user.role = 'owner'` 조인)

운영 중인 인스턴스의 실제 상태:

| 앨범 | 소유자 | 사진 | 현재 동작 | 원하는 동작 |
|---|---|---:|---|---|
| 건우카메라 | gunwoo | 4,662 | gunwoo 드라이브로 업로드 | 그대로 |
| 서희카메라 | seohui | 1,843 | **아무 일도 안 일어남** | **gunwoo 드라이브로** |
| 인화사진 | seohui | 63 | 아무 일도 안 일어남 | **계속 안 함 (명시적으로)** |
| test | gunwoo | 7 | gunwoo 드라이브로 업로드 | 안 함 |

서희카메라 1,843장이 "대기 중"으로 남아 있던 이유는 용량도 실패도 아니라, **소유자 계정이
구글드라이브에 연결된 적이 없어서**였다. 소유권과 백업 대상이 묶여 있는 한, 연결된 계정
하나로 가족 사진을 모으는 것이 불가능하다.

이 배포의 파이프라인은 Drive를 Pixel로 가는 경유지로 쓴다(로드맵 §0). Pixel은 한 대,
따라서 계정도 하나로 모여야 한다 — 소유권 기준 모델과 근본적으로 맞지 않는다.

## 2. 새 규칙

> **"업로드는 그 앨범을 선택한 사람의 드라이브로 간다."**

- 자기가 **볼 수 있는** 앨범(소유 또는 공유받음)을 선택할 수 있다.
- 업로드 대상은 언제나 **선택한 본인의 폴더**. 남의 드라이브에 쓰는 경로는 생기지 않는다.
- 여러 사람이 같은 앨범을 선택하면 각자의 드라이브로 각각 올라간다. 원장이
  `(userId, assetId)` 단위이므로 중복 방지도 사용자별로 자연스럽게 동작한다.

권한 모델이 정직해지는 것이 이 선택(검토했던 대안 A: "소유자가 대상 계정을 지정")보다
나은 이유다. A는 상대의 동의 없이 상대 드라이브에 쓰는 경로를 만든다.

## 3. 스키마

```
google_drive_album
  userId   uuid  FK user  ON DELETE CASCADE   ┐ PK (userId, albumId)
  albumId  uuid  FK album ON DELETE CASCADE   ┘
  createdAt timestamptz default now()
```

행의 존재 = "이 앨범을 내 드라이브에 백업한다". 별도 boolean 없음 — 해제는 행 삭제.
두 FK 모두 CASCADE라 사용자나 앨범이 사라지면 선택도 자동 정리된다.

### 마이그레이션 시딩 — (가) 현재 동작 보존

```sql
insert into google_drive_album ("userId", "albumId")
select au."userId", au."albumId"
from album_user au
join user_google_drive ugd on ugd."userId" = au."userId"
where au.role = 'owner';
```

**연결된 사용자가 소유한 앨범을 전부 선택 처리한다.** 이게 정확히 오늘의 동작이므로,
마이그레이션 직후 업로드 거동은 한 톨도 바뀌지 않는다. 사용자는 그다음 UI에서 원하는 대로
추가(서희카메라)·해제(test)하면 된다.

운영 인스턴스 기준 시딩 결과: gunwoo에게 건우카메라 + test 2건, seohui는 미연결이라 0건.

## 4. 코드 변경

### 4.1 큐잉 — 소유자 조회에서 선택자 조회로

`AlbumService`의 두 경로(`addAssets`, `addAssetsToAlbums`)는 지금 앨범당 소유자 **한 명**을
구해 큐잉한다. 앞으로는 앨범당 **선택자 N명**에게 각각 큐잉한다.

```
현재: getAlbumOwnerId(album) → queueGoogleDriveUploads(ownerId, assetIds)
변경: getSubscribers(albumId) → 각 userId마다 queueGoogleDriveUploads(userId, assetIds)
```

`getSubscribers`는 `google_drive_album`을 `user_google_drive`와 조인해 **선택했고 연결도
되어 있는** 사용자만 돌려준다(미연결자에게 큐잉해봐야 워커가 스킵할 뿐 — Wave 1에서
`autoSync` 논의 때 세운 원칙과 동일).

`getAlbumOwnerId`는 `syncAlbum`의 권한 검사에서만 계속 쓰이므로 남는다.

### 4.2 백필 — 조인 축을 바꾼다

`streamPendingUploads`의
`album_user.role = 'owner'` → `google_drive_album` 조인으로 교체. 나머지 조건(소프트 삭제
제외, 원장 anti-join, 차단 사용자 anti-join)은 그대로.

### 4.3 수동 동기화 — 소유자 전용 제한을 푼다

`syncAlbum`은 지금 소유자만 허용한다. 새 모델에서는 **"내가 선택한 앨범"이면 실행 가능**
해야 한다(공유받은 서희카메라를 건우가 동기화할 수 있어야 함).

- 권한: `Permission.AlbumRead` + 해당 앨범을 선택했을 것
- 업로드 대상: `auth.user.id` (소유자 아님)
- 선택하지 않은 앨범이면 400 + "먼저 이 앨범을 백업 대상으로 추가하세요"

### 4.4 API

```
GET    /google-drive/albums            → 내가 볼 수 있는 앨범 + 선택 여부 + 진행 카운트
PUT    /google-drive/albums/:id        → 선택 (AlbumRead 권한 검사)
DELETE /google-drive/albums/:id        → 해제
```

`PUT`은 선택과 동시에 그 앨범의 미업로드분을 큐잉한다(resume이 재큐잉하는 것과 같은
이유 — 켜자마자 시작되기를 기대하는 게 자연스럽다). `DELETE`는 이미 큐에 있는 작업까지
취소하지는 않는다(워커가 원장·연결만 확인하므로 소수가 더 올라갈 수 있음, 무해).

### 4.5 UI

**설정 → Google Drive Sync** 에 백업 대상 목록:

```
백업할 앨범
  ☑ 건우카메라        4,662장 · 4,655 업로드됨
  ☑ 서희카메라 (서희)  1,843장 · 대기 중
  ☐ 인화사진 (서희)      63장
  ☐ test                  7장 · 5 업로드됨
```

공유받은 앨범은 소유자 이름을 병기해 "남의 앨범을 내 드라이브에 백업한다"는 사실이
드러나게 한다. 카운트는 Wave 2의 status 집계를 앞당겨 쓰는 것 — 다만 Wave 2와 달리
**소유자 기준이 아니라 보는 사람 기준**이 된다(새 모델에서는 그게 맞는 축이다).

## 5. 영향 범위 점검

- **`syncAlbum`의 "소유자만" 주석/테스트**: 새 규칙으로 교체. 기존 보안 논거("공유 앨범
  편집자가 소유자 드라이브에 밀어 넣는 것 방지")는 여전히 성립한다 — 이제 자기 드라이브로만
  가므로 그 공격 자체가 불가능해진다.
- **Wave 2 계약**: 앨범 status의 "uploaded"를 소유자 기준으로 정의했었는데(로드맵 §3.1,
  리뷰 Q5), 이 Wave 이후에는 **보는 사람 기준**이 옳다. 로드맵 문서도 함께 고친다.
- **Wave 4 autoSync 토글**: 앨범 단위 선택이 생기면 계정 단위 토글의 필요성이 줄어든다.
  Wave 4에서 재검토.

## 5b. 접근 상실 처리 (리뷰 판정: 정확성 요구사항)

공유가 끊겨도 선택 행은 남는다(앨범·사용자에 독립적으로 FK). 처리 방침:

| | |
|---|---|
| 업로드 | 접근 조인이 없으면 즉시 **중단**. 선택 행만으로는 절대 큐잉하지 않는다 |
| 선택 행 | **유지**. 재공유되면 자동으로 재개된다 — 즉시 삭제하면 재공유 시 조용히 안 돌아온다 |
| UI | 선택 목록에 "접근 상실 — [소유자]가 공유를 중단했습니다"로 표시. 조용히 사라지지 않게 |
| 알림 | 접근 상실 전이 시 1회 (Wave 1의 전이당-1회 규율 재사용) |

"조용히 멈추는 백업"은 이 프로젝트가 계속 없애온 패턴이므로, 중단 자체는 필수지만
**중단됐다는 사실은 반드시 보여야 한다.**

## 6. 테스트 계획

- 시딩 마이그레이션이 현재 동작을 정확히 재현하는지(연결 사용자의 소유 앨범 = 선택됨)
- 선택자 2명인 앨범에 사진 추가 → 두 사용자에게 각각 큐잉
- 선택했지만 미연결인 사용자에게는 큐잉 안 함
- 선택 해제한 앨범은 큐잉 안 함
- 공유받은 앨범을 선택한 사용자가 `syncAlbum` 실행 가능 / 선택 안 했으면 400
- 백필이 선택 축으로 동작하고, 차단 사용자 제외는 그대로 유지
- `PUT`이 즉시 미업로드분을 큐잉하는지
- **제외가 선택을 이기는지**: 자산이 선택 앨범과 제외 앨범에 동시에 속하면 업로드되지 않음
- **접근 상실**: 공유 해제 후 선택 행이 남아 있어도 큐잉·백필 대상에서 빠지는지 / 재공유 시 재개
- **권한 등급**: 읽기만 가능한 공유 앨범은 선택·동기화가 거부되는지(`AlbumDownload` 필요)
- 시딩 후 구독자 집합이 기존 "연결된 소유자" 집합과 정확히 일치하는지 (리뷰 권고)

### 남은 원 질문 기록

1. **시딩 전략**: "연결된 사용자의 소유 앨범을 전부 선택" — 현재 동작 보존이 목적인데,
   더 안전한 대안이 있는가? (전부 해제 시작은 자동 업로드를 조용히 멈추므로 배제했다)
2. **`DELETE` 시 큐 정리 안 함**: 이미 큐에 있는 작업 몇 개가 더 올라갈 수 있다. 사용자가
   "끄기"를 눌렀는데 몇 장 더 올라가는 것을 수용 가능한가, 아니면 워커 입구에서 선택 여부를
   재확인해야 하는가? (재확인은 작업당 조회 1회 추가)
3. **선택자 N명 큐잉의 비용**: 앨범당 선택자 조회가 add-to-album마다 1회 추가된다. 지금
   구조(소유자 1명 조회)와 같은 차수이지만, 확인 요청.
4. **`syncAlbum` 권한 완화**: AlbumRead + 선택 여부로 바꾸는 것이 충분한가? 다운로드 권한과
   동급으로 봐야 하는가(Wave 4 선택 업로드에서 리뷰어가 요구했던 기준)?
5. **Wave 2 status의 축 변경**: 소유자 기준 → 보는 사람 기준 전환에 놓친 함의가 있는가?
